# Translating the interface

The UI supports `en`, `uk`, `pl`, `de`, `fr`, `es`, `it`, `pt-BR`, `cs`, `ro`, `nl` and `sk`. Settings defaults to the system language; unsupported system languages fall back to English. Users can change the interface language without changing document source/target languages, model choices or translation text. `FORMA_UI_LANGUAGE` can override the startup preference for testing.

`src/forma/localization/catalog.py` handles language resolution, catalogs and the Qt translator. Its immutable `LANGUAGE_METADATA` registry defines autonyms, locale, script and text direction; document translation and OCR have independent capability lists. Locale matching first tries the exact normalized code, then parent language codes. For example, `PT_br` resolves to `pt-BR`, `fr-CA` to `fr`, and unsupported Portuguese regions fall back to Brazilian Portuguese. Existing saved language codes remain valid. Locale JSON files in `src/forma/locales/` map the original Ukrainian UI strings to translated strings. Ukrainian uses the original text. QML uses `qsTr()`; Python UI boundaries use `translate()`. The backend stores canonical messages and review fingerprints independently from UI translations.

## Adding or correcting text

- Update every registered non-Ukrainian catalog for new visible UI strings. Tests derive their language sets from the registry. Keep the wording short enough for the minimum 960 × 680 window.
- Preserve `%1`, `%2` placeholders in QML strings and named `{value}` placeholders in Python templates exactly. Do not translate identifiers or values captured from a message.
- Do not translate document contents, paths, model IDs, protocol values or persisted review fingerprints through the UI catalog.
- A new language needs a metadata entry and complete catalogs, followed by runtime switching tests. Do not copy English values as a placeholder or treat a fallback as a completed translation. Preserve regional codes such as `pt-BR` in preferences and filenames.
- Native OS dialogs keep platform styling. Qt fallback dialogs use Qt's own translations where installed.

Run `uv run pytest tests/test_i18n.py tests/test_backend_i18n.py` and the full suite before submitting changes. Verify runtime switching, persisted preference, source/target selector stability, review edits and long labels in every registered language, in both light and dark themes. Changing interface language must never trigger an API call.

Translation-memory controls and errors belong to the registered catalogs: existing split catalogs use `*_memory.json`, while merged catalogs such as `nl.json` and `sk.json` contain the same keys directly. Ukrainian catalogs include translations of storage errors whose canonical source is English. Project names, glossary terms, reference paths, source/target wording, memory keys and approval revisions remain unchanged when the interface language switches. Check both memory dialogs with unsaved fields and an open preferred-wording conflict; switching languages must preserve the selected project, draft paths, approval choice and comparison text.

## Expansion waves and review status

The first expansion added Italian, Brazilian Portuguese, Czech and Romanian. The second adds Dutch (`Nederlands`, `nl_NL`) and Slovak (`Slovenčina`, `sk_SK`), bringing the registry to twelve interfaces. Dutch and Slovak use complete merged catalogs covering the same source keys as the existing languages, including document formats, reports and project memory. Regional variants such as `nl-BE` and `sk-SK` resolve to the base catalog, independently from the languages used to translate documents or run OCR.

These expansion catalogs are model-generated and checked for key coverage, placeholders, terminology and live switching. They have not undergone professional native-speaker review. Correct awkward wording through ordinary catalog changes without changing canonical reports or document text.

The current registry contains left-to-right interfaces. Direction metadata alone does not enable right-to-left layouts. Adding Arabic or Hebrew also requires layout mirroring, bidirectional text and navigation tests. Adding Chinese or Japanese requires checking font fallback, line breaks and input methods in packaged applications. Region/script-aware matching is ready for distinct future catalog codes such as `pt-PT` or `zh-Hant`, but those catalogs are not currently provided.

## Integer count forms

`plural_category()` and `translate_count()` provide integer cardinal forms using the [Unicode CLDR rules](https://www.unicode.org/cldr/charts/50/supplemental/language_plural_rules.html). The registry specifies the rule for each interface language. Flat string catalogs under `locales/plurals/` contain singular and plural variants, keeping the ordinary catalog schema unchanged. Counts must be non-negative integers; numeric strings are accepted when rendering already-formatted canonical statuses. Fractions and ordinals are outside this helper's scope.

The first integrated messages are ready segment counts, ready page counts and the added-glossary-terms notice. Both explicit `{count}` values and canonical formatted statuses select the correct form at presentation boundaries. The Qt translator also forwards its `n` argument for supported `%n` count sources. Canonical stored messages, fingerprints, document contents and JSON reports remain unchanged. Tests cover 0, 1, 2, 5, 11 and 21 in every language, including the different Ukrainian, Polish, Czech, Romanian and Slovak forms, plus million categories where required. Dutch uses singular only for integer 1. Slovak uses singular for 1, the few form for 2–4 and the other form for 0 and 5 or more; 21, 22 and 101 do not restart that pattern.
