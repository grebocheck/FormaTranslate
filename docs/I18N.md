# Translating the interface

The UI supports `en`, `uk`, `pl` and `de`. Settings defaults to the system language; unsupported system languages fall back to English. Users can change the interface language without changing document source/target languages, model choices or translation text. `FORMA_UI_LANGUAGE` can override the startup preference for testing.

`src/forma/i18n.py` handles language resolution, catalogs and the Qt translator. Locale JSON files in `src/forma/locales/` map the original Ukrainian UI strings to translated strings. Ukrainian uses the original text. QML uses `qsTr()`; Python UI boundaries use `translate()`. The backend stores canonical messages and review fingerprints independently from UI translations.

## Adding or correcting text

- Update all English, Polish and German catalogs for new visible UI strings. Keep the wording short enough for the minimum 960 × 680 window.
- Preserve `%1`, `%2` placeholders in QML strings and named `{value}` placeholders in Python templates exactly. Do not translate identifiers or values captured from a message.
- Do not translate document contents, paths, model IDs, protocol values or persisted review fingerprints through the UI catalog.
- A new language also needs a language entry, a supported-code update and complete catalogs, followed by runtime switching tests.
- Native OS dialogs keep platform styling. Qt fallback dialogs use Qt's own translations where installed.

Run `uv run pytest tests/test_i18n.py tests/test_backend_i18n.py` and the full suite before submitting changes. Verify runtime switching, persisted preference, source/target selector stability, review edits and long German labels. Changing interface language must never trigger an API call.
